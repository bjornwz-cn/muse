## 1. 做了什么（王震 2026-11-20 亲定）

复核队列原来是文件级、无文件夹概念，一个程序包（如 PaddleOCR-3.7.0、项目开发/企业固定资产管理系统）能刷出上百条模糊/低置信噪音。0.1.6 改为文件夹级复核：

1. **队列按文件夹分组展示**：同一文件夹下的待复核项合并为一张文件夹卡片，显示文件夹路径、条数、类型分布（blur/low_conf/ambiguous/sensitive/dup 各几条）。卡片上一次决定对该文件夹下全部待复核项生效；单条仍可点开展开逐条处理；现有单条/批量接口不变。
2. **文件夹整体移动**：卡片上改顶层（工作/家庭/媒体）后批准，整包移动——逐条复用 `api/review.py` 的 `_recompute_dst_for_top` 逻辑（只换库根、子路径保留）；拒绝只改状态、不动文件；dup 项仍按 holding 区规则（0.1.2），不受改顶层影响。
3. **后端**：新端点 `GET /api/review/folders`（status=pending/approved/rejected/all，kind 可选）与 `POST /api/review/folders/approve|reject`；原有 `/api/review` 列表与单条/批量 decide 接口未动，向后兼容。

### 分组规则（`common/routing.py` 的 `review_folder_for()`，纯函数）

- 分组键 `"<top>:<rel_folder>"`，如 `mac-backup:项目开发`、`mac-backup:下载/PaddleOCR-3.7.0`、`family:刘音`。
- 通用容器名（下载/Download/桌面/Desktop/文稿/Documents）下钻一级、至多三级：如 `下载/PaddleOCR-3.7.0` 不会把整个「下载」并成一张卡。
- 不在任何库根下为 `other:`；直接在库根下 rel 为空。

## 6. 部署事故与修复（已处理，无残留）

部署中连续踩了两个坑，均已修复并核实，真实 DB 与 /vol1 未受影响：

1. **compose 拷错路径**：fnpack 包内解出的 compose 在 `docker/docker-compose.yaml`（不是 `app/docker/docker-compose.yaml`），第一次 `cp` 失败导致旧 compose（0.1.5）未被替换。修正：用解包后的正确路径重拷，diff 确认只差注释与镜像标签。
2. **`VAR=val sudo docker compose` 传不进环境变量**：sudo 会剥掉前缀的环境变量，容器以空的 TRIM_* 变量启动，/data 被挂成宿主根目录下的 `/@appshare/data`（docker 自动新建的空目录），并跑起了 0.1.5 镜像。发现后立即停容器，删掉误建的 `/@appshare/data`（内含刚初始化的空库 135KB、config、logs，约 1 分钟内未跑任何任务，未动真实数据）。修正：改用 `sudo env TRIM_SERVICE_PORT=8765 TRIM_APPDEST_VOL=vol2 TRIM_APPNAME=nas-curator docker compose …` 重建，挂载核实正确。
   - **教训**：`appcenter-cli stop` 不可靠、force-recreate 绕法仍在用，但今后每次 force-recreate 后必须先核对 `docker inspect` 的挂载与镜像再放行（本次就是靠这一步发现的）。`scripts/upgrade.sh` 里同款 `VAR=val sudo docker compose` 写法有同一隐患，下个版本修（改 `sudo env …`）。
   - 另：`scripts/sync-code-to-nas.sh` 与本报告的部署流程本身没问题。

### Dockerfile LABEL 移到末尾（有意修复）

之前 LABEL version 在 pip 层之前，版本号一改即 bust 全部缓存，全量构建须重装依赖并常在下载 torch 时 stall；已移到文件末尾，下次一键升级的全量构建可复用 pip 层缓存。本次快路构建不受此影响（约 7 秒）。

## 7. 新发现：模型配置第 4 处问题——两把 Ark Key 存了但没生效

0.1.6 部署验证时顺带查到（与 0.1.6 代码无关，0.1.5 时已是这个状态）：

- 现状：`/api/settings` 显示三行模型 key_set 全为 False，实际生效顺序只有 `local`（本地 Ollama qwen3:4b）。**两把云模型当前根本不在调用链里，分类全走本地。**
- 原因：`/data/config/.env.local`（600，2026-11-20 09:42 写）里有两把 46 字符的 Key，但变量名是 `LLM_KEY_AGENT_PLAN` 与 `LLM_KEY_MODEL_3`；而模型列表（11:15 保存）的 key_env 字段是 `ARK_PLAN_KEY` 与 `ARK_PAYG_KEY`。`_resolve_key` 只按 key_env 名查找，名对不上 → 两行被跳过。
- 根因（代码已核实，`common/llm_models.py:138`）：自定义行保存时若未填 key_env，系统自动派生 `LLM_KEY_<行ID>`；王震先保存时 Key 就写进了这两个派生名下，11:15 重保存时把 key_env 改成了 ARK_* 却没重贴 Key，旧名下的值就没人认了。Key 本身没丢、没泄露，值完好在文件里（本次只查了变量名与值长度，未读取、未复述任何 Key 值）。
- 修复（二选一，**未动手，等王震定**）：①在设置页把两把 Key 重新贴进两行的 Key 栏再保存（会按 ARK_* 名重写进 .env.local）；②由 muse 把 .env.local 里两个变量名改成 ARK_PLAN_KEY / ARK_PAYG_KEY（只改名、不动值、不复制）。无论选哪个，仍须先修之前三处错误（模型 ID `auto` 无效、第三行 Endpoint 多一段 `/chat/completions`、计费标反），修完后 muse 再验证云模型是否真通。
