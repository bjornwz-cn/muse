## 8. 与任务书的偏差（须父代理知晓）

### 8.1 镜像在 NAS 上构建，不在 VM 上（最大偏差）
- **原因**：VM → NAS 隧道带宽实测仅约 **55KB/s**（单流 60KB/s、8 流并行聚合约 50KB/s，不提速；直连 Tailscale IP 被禁 "Operation not permitted"；gh 未登录、无可用的 registry 凭据，ghcr.io 推不上去）。1.53GB 镜像传过去需约 **7 小时**，不可行。
- **做法**：把构建上下文（Dockerfile + requirements + 应用代码，仅 169KB）传到 NAS，在 NAS 上 `docker build`（同一份 Dockerfile + requirements-image.lock，包版本一致）。NAS 侧：基础镜像经 daocloud 镜像拉取（docker.fnnas.com 401，见下）；pip 走清华 PyPI 镜像（阿里云镜像缺 fastapi 0.165.0，见下）；apt 走 deb.debian.org（慢，约 18 分钟）。
- **等价性**：NAS 镜像与 VM 手工组装镜像用同一份 Dockerfile、同一份 lock、同一份应用代码；包版本一致（torch 2.15.0+cpu、transformers 4.57.1 等）。**唯一差异**：NAS 的 python:3.12-slim 是 Debian 13（trixie，daocloud 新拉的），VM 的是 Debian 12（bookworm）；Python 均为 3.12，应用代码相同。
- **VM 手工组装的镜像仍在** ~/workspace/nas-curator-image/nas-curator-0.1.0.tar（1.53GB，docker load 验证通过），可作备份；若日后隧道带宽恢复，可传过去比对/替换。

### 8.2 /vol1/1000 挂载为 RW（任务书写“只读挂载三个库 + 读写统一收件箱”）
- 任务书的只读挂载与 App 核心功能冲突：归位必须把文件**移入**三个库，只读挂载会使 apply 报 EROFS、功能不可用。故挂整个 /vol1/1000:rw。安全控制靠 guard.py 排除规则 + App 自身逻辑，不是靠只读挂载。挂载探针（§4）已验证读写均正常。

### 8.3 容器以 root 运行（任务书/架构写 UID/GID 1000）
- /vol1/1000 为 mode 000 + fnOS trimacl；实测属主 bjorn（uid 1000）可读写，但容器内以 uid 1000 跑时 /data（@appshare，属主 docker-nas-curator，mode 700）写不了。现有 fnOS Docker 应用（Home Assistant 等）均以 root 运行。归位后文件仍 chown 1000:1000，属主不变。

### 8.4 数据卷用 fnOS 标准 @appshare（任务书建议 /vol1/1000/收件箱/.curator 或 /vol2/docker/nas-curator/data）
- 前者在收件箱内（会被收件箱扫描误处理）；后者需安装时建目录并改属主，且污染 docker 数据根目录。改用 `/${TRIM_APPDEST_VOL}/@appshare/${TRIM_APPNAME}/data`（fnOS 标准 data-share，由安装器自动建，随用户选的安装卷走），DB/config/日志在内。

### 8.5 SEM_HOST 是 11500，不是 11434（我初版写错，已修正）
- bge-m3 只在 ollama-gpu（11500）上有，ollama-cpu（11434）上只有 qwen3:8b/4b/30b 与 bge-reranker。代码默认值本就是 11500（deps.py DEFAULT_SEM_HOST、semkit.py 默认 host、curator.py:108），setup.html 表单默认值也是 11500；是我首次向导提交（curl）与 Dockerfile/compose 里误写成 11434，导致语义模型一度不可用。已修正：源码三处 + 运行中 App 的设置文件（经 /api/setup）+ 已安装的 compose（改后用 compose --force-recreate 重建容器，appcenter 的 stop/start 不重建容器）。
- 另：直接用 `docker compose` 重建时须带齐 TRIM_SERVICE_PORT=8765、TRIM_APPDEST_VOL=vol2、TRIM_APPNAME=nas-curator，否则变量展开为空会导致端口变随机（曾变 32768）与 /data 挂到错误的 `/@appshare/data`（曾在宿主根目录建出 stray 目录，已删；真实 DB 未受影响）。

### 8.6 NAS 构建中的两个源问题（已解决）
- 基础镜像：NAS 的 docker 镜像源 docker.fnnas.com 对 python:3.12-slim 报 401。改从 daocloud 拉取（`docker pull docker.m.daocloud.io/library/python:3.12-slim` 后 tag 为 python:3.12-slim），一次成功（119MB）。
- PyPI 镜像：阿里云镜像缺 fastapi 0.165.0（只到 0.164.0），pip 报 No matching distribution。改清华镜像（有 0.165.0），构建通过。Dockerfile 已加 `PIP_EXTRA_INDEX_URL` build arg（默认 pypi.org，NAS 构建传清华）。

### 8.7 运行中的 0.1.0 与 dist/ 的 .fpk 有两处细微不一致（不重装）
- dist/ 的 .fpk（md5 dfc7096ad20b5be16cf04467a824bf1b）已含 HF_HUB_CACHE 与 entrypoint 的 `--out /data/plan_inbox.csv`（plan CSV 写持久卷而非镜像内 /app/data）；运行中的 App 是此前一次打包安装的，无这两处，但功能均正常（SigLIP 走兜底、plan CSV 目前写 /app/data 临时位置，DB 为准）。下次升级时自然对齐，无需为此重装。
