## 2. 【关键发现】内容标签从未落库

### 证据

**证据一：代码里有个写了没用的函数**

`common/tags.py:167` 有 `attach_tags(conn, file_id, tags)`，注释写得很清楚：
```
tags: list of (name, kind, confidence, source)。写 file_tags。
```
**全仓搜索：除定义处外，零调用。**

`common/db.py:111 upsert_file()` 同理——生产代码里**没有任何地方调用**（只有 `scripts/migrate_p4.py` 的批量迁移和一处测试）。

**证据二：媒体库 59,453 个文件，标签全空**

我直接查了 `/api/browse` 的媒体库照片目录：

```
照片/家庭与人物/人物合影/000bfa156dc370ea6318f47c6f04722f.JPG | status: active | tags: None
照片/家庭与人物/人物合影/009d0948c82e38fecdd644562ebb2c4c.JPG | status: active | tags: None
照片/家庭与人物/人物合影/01fa1e237f34ddf8a7d88f2d48816148.JPG | status: active | tags: None
⋯（连续 8 条，全部 None）
```

### 为什么会这样

自动归位的链路是：

```
plan_item 生成 → tags 字段填好（如 ['人物合影','照片']）
  ↓
_apply_items / _run_auto_apply
  ↓
CE.apply_plan(items, root, dry_run=False, uid, gid)   ← 只做文件系统操作
  ↓
DB.add_operation(...)                                  ← 只记 src/dst/sha256
  ✗ 没有 upsert_file → 没有 file_id
  ✗ 没有 attach_tags → file_tags 表永远空
```

`apply_plan` 的签名是 `def apply_plan(items, root, *, dry_run, uid, gid, keep_review)`——**它根本不接数据库连接**。

唯一写 `file_tags` 的地方是 `api/review.py:241 _persist_tags()`，而它前面有一道门：

```python
"""复核时用户给的 tags：文件已在 files 表登记时才写 file_tags；未登记则忽略。"""
row = DB.get_file_by_path(conn, file_path)
if not row:
    return          # ← 自动归位的文件从没进 files 表，所以永远在这里 return
```

**结果：自动归位的文件，内容识别结果全部丢失。**

### 后果

1. **搜不到**：`/api/browse?tag=儿童成长` 查不到任何刚归位的照片。
2. **照片库 5.9 万个文件，标签表是空的**——等于把所有内容识别的工作白做了。
3. 你在复核页看到的 `tags: ['工作与活动','照片']`，**批完就扔**。

### 建议（P0，改动很小）

在自动归位成功后补两步：

```python
# curator.py::_apply_items 与 api/jobs.py::_run_auto_apply 各一份
for op, item in zip(operations, todo_moved):
    fid = DB.upsert_file(conn, op["dst_path"],
                         sha256=item.get("sha256") or "",
                         size=item.get("size"),
                         kind="media" if item.get("kind")=="media" else "document",
                         ext=item.get("ext"))
    from common.tags import attach_tags
    attach_tags(conn, fid, [(t, "scene", 0.7, "auto") for t in (item.get("tags") or [])])
```

同时给 `files` 表补一个 `content_category` 列（或复用 `file_text`），把分类器结论存下来。

**附带收益**：`_persist_tags` 的"文件未登记则忽略"从此不再是死路，人工复核时补的标签也能真正落库。

## 3. 位置与内容解耦：把"放哪"和"是什么"分开

王震原话是"**同意按确定性定位置，但同时要关注内容**"。这两件事不该互相绑死：

### 现状（绑死）

```
分类器判不出内容 → 不进库 → 位置也定不了 → 人工
```

### 目标（解耦）

```
第一层：位置（确定性优先，0 人工）
  EXIF 日期 → 照片/2023/2023-08/
  文件名年份 → 同上
  来源目录 → 同上
  兜底 → 照片/未分类/

第二层：内容（并行识别，不影响位置）
  SigLIP 12 类 → 高置信写 scene 标签
  VLM 看图 → 中置信写 scene 标签
  文本/OCR → 写 biztype / entity 标签
  识别不出 → 留空，以后 VLM 补

第三层：查询
  位置给"顺手翻"，标签给"精确搜"
  "2023年8月孩子" = 目录 2023/2023-08 + 标签 儿童成长
```

### 具体建议

1. **媒体归位改为时间轴**（0.2.5 已做，但只对新文件）：
   - 有 EXIF/文件名日期 → `照片|视频/<年>/<年-月>/`
   - 无日期 → `照片|视频/未分类/`（**不占人工**）
   - 内容类目**只做标签**，不再作为目录
2. **存量 5.9 万媒体做一次"内容补标"**（见 §4）
3. **复核页保留内容结论**：现在 `tags` 有值但批完丢弃，修完 P0 后自动入库

## 4. 存量内容补标：让 5.9 万个老文件也能搜

**现状**：媒体库 59,453 文件 / 689GB，标签为空。

**建议分三步，都可断点续跑**：

| 步 | 做什么 | 耗时估 | 产出 |
|---|---|---|---|
| A | 读 EXIF + 文件名 → 写 `year`/`month` 标签，修正位置 | 快（只读文件头） | 全部有日期轴 |
| B | SigLIP 打 scene 标签（现有模型，不花钱） | 中（约 5.9 万张） | 大部分有场景标签 |
| C | VLM 补低置信项（现有 Ark/Ollama 链路） | 慢（按需） | 补齐难判的 |

**注意**：B/C 只写标签、**不动文件位置**，所以风险极低，可以一直跑。
