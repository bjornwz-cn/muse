## 1. 问题 1：总览页白屏（JS 语法错误）

### 根因

`web/templates/index.html` 第 133–134 行，`var cards = (d.libraries || []).map(function (lib) {` 重复了一行，致内联 `<script>` 解析失败，`load()` 从不执行，总览页永久“加载中...”。

- 证据：抽出内联脚本跑 `node --check` 报 `SyntaxError: missing ) after argument list`（在 `} catch (e) {` 处）；线上容器 `/app/web/templates/index.html` 同样有重复行。
- 引入点：`git log -S` 显示重复行是 0.1.4（commit `fe761d0`，半自动升级）引入的，0.1.1 初版没有。
- 漏网原因：此前各版本验收只查六页 HTTP 200，没查 JS 解析。

### 修法

删掉重复的一行（`var cards` 出现次数 2→1）。其余不动。

### 回归测试

新文件 `tests/test_template_js.py`：抽取全部 7 个模板的内联 `<script>` 跑 `node --check`，任一模板语法错即失败。当前 7 个模板各 1 段内联脚本，均无 Jinja 插值；node 缺失时 skip；脚本含 Jinja 插值时失败（插值后的 JS 不可直接校验，须先改写法）。

反向验证已做：临时把重复行加回去，测试如期失败，随后恢复文件（重复行计数回 1）。

## 2. 问题 2：任务表是空的（CLI/API 发起的任务无记录）

### 根因

只有 POST `/api/jobs`（Web 发起）才写 jobs 行（`api/jobs.py` 的 `_run_plan_job`），`curator.py` 的 `cmd_plan` / `cmd_apply` / `cmd_rollback` 从不写 jobs 行。部署前实测：`GET /api/jobs?limit=20` 返回 `[]`（200），DB 里 jobs 表 0 行，但 plans 表已有 77 个计划（含 P4 各批与当天 CLI 跑的 plan 77–80）。

### 修法

用 `common/db.py` 已有的 `create_job` / `finish_job`（`api/jobs.py` 同款用法），在 `curator.py` 的 `cmd_plan`、`cmd_apply`、`cmd_rollback` 入口包一层 job 记录：

- 开始建行（status=running，kind=plan/apply/rollback，summary 带 `source=cli` 与 root），结束 finish 为 done/failed（summary 带 plan_id 与 move/review 计数；失败带 error）。
- 新增 `_record_job(args)`（CLI 默认记；API 以 `args._record_job=False` 跳过）与 `_CliJob` 类（建行即 running，`done()`/`fail()` 收尾；**job 行写失败绝不阻塞主流程**，建行/收尾失败时静默跳过）。
- `cmd_plan` 在 DB connect 后、guard 之前建行，所以 guard 拒绝（ValueError）也会记 failed 行。
- `cmd_apply` 的 summary 带 plan_id/moved/failed/root/dry_run；`cmd_rollback` 带 plan_id/moved/missing/failed/dry_run。
- 收件箱监听（`inbox --watch --apply --llm --sem`，entrypoint.sh 后台起，每 30 分钟一轮，`cmd_inbox` 的 `once()` 直接调 `_dispatch_plan` 而不走 `cmd_plan`）：已包上。**每 30 分钟的收件箱空扫不得刷屏任务列表**——0 项的自动扫描不留行，有动作或失败才留行；手动 CLI / API / Web 发起的任务无论 0 项与否都要留行。失败任何模式都留 failed 行（`_record_inbox_failure`，记录本身失败不掩盖原始异常）。
- `api/jobs.py` 三处命名空间已加 `_record_job=False`（`_plan_namespace`、`_run_cmd_apply`、`_run_rollback`），API 发起的任务不重复记行。

`GET /api/jobs` 与总览 `jobs_recent` 读的就是 jobs 表（`api/dashboard.py` 直接查 jobs 表 LIMIT 5；`/api/jobs` 查 LIMIT 20），新行与回填行自动显示。

### 回填

新脚本 `scripts/backfill_jobs.py`（纯 sqlite3，不依赖项目 import，可经 `docker exec` 喂 stdin 跑；幂等；`--dry-run` 预演）。只写 jobs 表，不动 plans/plan_items。

**一处与任务书字面的偏离（已说明原因）**：任务书说给所有无 job 行的计划回填，本实现只补 plan_items 总数 > 0 的计划，0 项的收件箱自动空扫不补——补了就是把“空扫刷屏”从未来搬到历史里，与 0.1.7 的不刷屏口径相悖。move/review 数按 plan_items 的 action 现算（inbox 计划的 summary 已被执行报告覆盖，无 n/move/review 字段）。

live 预演与实跑一致：**回填 14 行**（plan 8、10、11、12、14、15、16、17、23、24、27、77、78、79；13 与 80 是 0 项，全部 63 个 0 项计划跳过）。

### 回归测试

新文件 `tests/test_cli_jobs.py`（6 个测试）：

1. CLI plan 跑完 jobs 表多一行 done 行且 summary 含 plan_id；
2. 失败的 plan（排除路径 `/vol1/1000/下载/Wangzhen-Mac/muse`，guard 抛 ValueError）记 failed 行且 plans 表无新增；
3. CLI apply 记 done 行且 tmp 内文件真实移动；
4. CLI rollback 记 done 行且 tmp 内文件真实回滚；
5. 收件箱自动空扫（`--watch --max-runs 1`）plan 留行、jobs 不留行；
6. 收件箱手动单次空扫留 done 行；收件箱自动扫描有文件时留 done 行，source=inbox-watch。

注意：watch 有文件测试须把文件 mtime 拨回 10 分钟前，否则 settle（默认 3 分钟）会当“未稳定”跳过；`--settle-minutes 0` 因 `or` 回退到 config 的 3 而无效。

## 5. 部署事故与修复（已处理，无残留）

**第一次 force-recreate 失败（项目名错）**：直接跑 `docker compose up -d --force-recreate` 时，compose 把项目名取为工作目录名 `docker`（`/vol2/@appcenter/nas-curator/docker` 的 basename），不是 `nas-curator`。结果：新建了无用网络 `docker_default`，并试图新建同名容器，与正在跑的旧容器冲突（`Conflict. The container name "/nas-curator" is already in use`），旧容器 0.1.6 继续跑，未受影响。

修正：删掉无用网络 `docker_default`，改跑 `docker compose -p nas-curator up -d --force-recreate`，一次成功。

- **教训**：从 `/vol2/@appcenter/nas-curator/docker` 跑 compose 必须带 `-p nas-curator`（或 `COMPOSE_PROJECT_NAME=nas-curator`），P9 报告里的 `docker compose …` 写法有歧义，下次部署须写全。`scripts/upgrade.sh` 里如有同款裸 `docker compose` 调用，一并检查（与 P9 §6 的 sudo 环境变量隐患同批修，见 §8）。
- force-recreate 后核对挂载与镜像（P9 §6 教训，本次照做）：镜像 `sha256:cf6cee302286…`（即新构建的 0.1.7），LABEL version 0.1.7，project `nas-curator`，网络 `nas-curator_default`；挂载三项正确：`/vol1/1000 -> /vol1/1000`、models 只读挂载、` /vol2/@appshare/nas-curator/data -> /data`（真实数据目录，非 0.1.6 事故里的宿主根 `/@appshare/data`）。
