# P13 报告：任务进度系统（0.2.0）

日期：2026-11-23
版本：0.2.0（主体 commit 28b2705；收尾补丁至 23dd43e，见 §6）
需求来源：王震 2026-11-23 15:19 反馈——软件界面看不到每个任务的工作进度，
要求能看到进度、预估时间、已完成/待处理/问题数量，做成专业的系统。

## 1. 现状与根因

- 任务页 `web/templates/jobs.html` 只有任务历史表（任务/类型/状态/开始/结束），
  没有任何进度信息；API `api/jobs.py` 的 `GET /api/jobs` 只返回最近 20 个 job
  的原始行（含 summary JSON），`GET /api/jobs/{id}` 返回 job+plan+items
  （最多 200 项），没有任何进度计算（无按状态计数、无百分比、无速率、无 ETA）。
- 任务有两类来源：(1) Web API 发起的 plan/apply/rollback（jobs 表有行，
  plan_items 有状态）；(2) CLI 脚本直接跑的（如 vlm_reclassify.py、
  vlm_apply.py、dedup 脚本，只建 plans、不建 jobs 行）。第二类在界面上
  完全不可见——这正是 61 小时媒体批、14,315 项年份重分类等长任务
  “看不到进度”的根因（当时唯一进度信号是容器 CPU/日志）。

## 2. 设计

### 2.1 进度计算（DB 任务）

新模块 `common/progress.py` 的 `compute_progress()`（纯函数）：
- 计数：`total/done/pending/skipped/failed`，pending = total − done − skipped − failed
  （下限 0）；pct = (done + skipped) / total——skipped 是已决定的不做项
  （如已在目标位置），计入已解决；failed 是问题，不计入。总数 0 且已结束时
  pct 按 100 计（收尾补丁，见 §6）。
- 速率：已耗时 ≥ 60 秒且 done > 0 时才算（项/分钟）；否则 None。
- ETA：剩余 pending / 速率；无速率或 pending 为 0 时 None。
- ETA 算不出来一律返回 None，前端显示 “—”，绝不编造数字。

`api/jobs.py` 的 `_job_progress()`：有 plan 的任务按 plan_items 的
`GROUP BY status` 实时计数；无 plan 且已结束的按 job summary 计数算 100%；
无 plan 且进行中的总数未知（total/pct/ETA 全为 None）。
阶段（phase）：plan 状态优先（applying→执行中、done→已完成），其次按任务类型
（plan→计划中、apply→执行中、rollback→回滚中）。
plan 扫描中途（plan_items 尚未写入）时 total 为 0、phase 显示计划中——
总数未知时不编造。
收尾补丁（§6）：(a) plan/rollback 任务按任务本身计进度——已完成的 plan 任务
（计划已生成）按 100% 计，不按 plan_items 状态（否则全 pending 的计划会显示 0%）；
(b) apply 任务的工作集只计非 review 项（review 项从来不是 apply 要移动的，
否则 #107 的 31,493 个 review 项会让进度永远到不了 100%）；(c) 已完成的 apply
任务若 plan_items 状态从未被写过（CLI apply 不写项状态，#107/#142 的项至今全是
pending），以 job summary 的 moved/failed 兜底——done 取项状态与 summary 的最大值，
剩余未移动项（已在目标位置）计 skipped、pending 归零；进行中/失败的任务不用兜底，
如实显示项状态。

### 2.2 脚本任务心跳契约

CLI 脚本在 `<DB 同目录>/progress/<任务标识>.json` 写进度（原子写：临时文件 +
os.replace），字段：task_id / label / kind / phase / status（running/done/failed）/
total / done / skipped / failed / errors（最近 10 条）/ started_at / updated_at /
extra。`common/progress.py` 的 `write_heartbeat()` / `read_heartbeats()` 负责读写；
心跳文件过期（updated_at 超过 10 分钟且 status 仍为 running）标 stale
（已失联/可能中断），绝不假装还在跑。心跳写失败绝不影响主流程（best-effort，
只打印一行）。

已接心跳的脚本（同一任务标识复用，阶段递进）：
- `vlm_reclassify.py`：标识 `vlm-reclassify`（`--heartbeat-id` 可改），阶段 vlm，
  每 100 项写一次；年份重分类的 VLM 阶段传 `--heartbeat-id year-reclassify`。
- `vlm_apply.py`：标识 `vlm-apply`，阶段 analyze（每 500 项）/ apply（每 100 项）。
- `year_siglip.py` / `year_register.py` / `year_summary.py`：同一标识
  `year-reclassify`，阶段 siglip → register → vlm → summary。

### 2.3 兜底推导（正在跑的旧版 year_siglip）

部署时年份重分类的 SigLIP 正在跑（/data 里是旧版脚本，不写心跳），
`common/progress.py` 的 `derive_year_progress()` 从脚本自己产出的真实产物推导，
source 标 `derived`、与心跳来源区分：
- 已分类数 = `/data/year_siglip_results.jsonl` 行数（逐行刷盘）；
- 总数与已耗时 = `/data/year_siglip.log` 最后一行 `PROG d/t secs`（每 200 项打印一次），
  总数取不到时用 `to classify (SigLIP): N` 那行；
- 汇总文件 `year_reclassify_summary.json` 存在即视为本阶段跑完（status done）。
产物都不存在时返回 None（任务尚未开始）。
- 收尾补丁（§6）：derived 改为阶段感知——`year_vlm*.log` 存在即当前阶段是 VLM
  （done 按 OK rq id 跨日志去重，total 取各日志 "to process" 的最大值）；
  `year_vlm_rqids.txt` 非空且无 VLM 日志时是 register 已完成、VLM 未启动的间隙
  （阶段记 vlm、done 0、stale 恒 False）。判定逻辑：阶段跑满（done ≥ total）
  即 status done、不标 stale；进行中但最新产物超过 10 分钟未更新才标 stale
  （真中断）。心跳路径本身已是这条规则（status running 才判 stale，
  且 `vlm_reclassify.py` 正常结束会写一条 status done 的终态心跳）。

### 2.4 接口

- `GET /api/jobs`：每个 job 带 `progress` 摘要（计数+百分比+ETA），不加载 items。
- `GET /api/jobs/{id}`：同上（原有 job+plan+items 不变）。
- `GET /api/jobs/{id}/progress`（新增）：进度详情 + 问题清单
  （plan_items 里 status='failed' 的项，含 src_path/reason，最多 50 项）
  + failed 总数。
- `GET /api/jobs/running`（新增）：DB 侧 status='running' 的 job（带进度）
  + 脚本任务（心跳 + derived；running/stale 全列，1 小时内刚结束的 done 也列，
  更早结束的不再列出）。心跳与 derived 同 task_id 时只留心跳（心跳为准）。

## 7. 事故（必须如实记录）

### 7.1 Git：amend＋force-push 覆盖了耳机助手提交（约 16:05）

用 `git commit --amend`＋`--force-with-lease` 推送 0.2.0 时，覆盖了远端已有的
耳机助手 0.9.2 两个提交（67c0e59、89da77b）——远端在 15:50 后多了这两笔提交，
而 amend 的基底是旧的 4bbeb22，lease 检查因本地 remote-tracking ref 已被他人
fetch 更新而通过。发现后立即恢复：本地 reset 到 89da77b，把 fix 作为新提交
016b9b4 加在其上，用 pin 到 d14c425 的 lease 推回，核实远端 HEAD=016b9b4，
历史为 28b2705→67c0e59→89da77b→016b9b4，`update/latest.json` 恢复为
versionCode 50 / 0.9.2。远端在约 15 分钟窗口内 served 0.9.1（versionCode 49），
若用户在此窗口内检查更新会看到 0.9.1；jsDelivr 可能短暂缓存过任一版本。
教训：共享仓提交前必须先 fetch＋rebase，amend＋force-push 在多人共享仓是
危险操作；此后所有推送均直推、无 force。
