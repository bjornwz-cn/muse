# NAS Curator 统一架构设计 v1.0

2026-11-19 · 合并 workfiles-curator v3.1.1 + media-library-curator 为一个飞牛 App

## 0. 产品定义

### 0.0 定案（2026-11-19 王震确认）

| 事项 | 定案 |
| --- | --- |
| 合并 | workfiles-curator + media-library-curator 合成一个 App，先合并再修库 |
| 大分类 | 三大类：**工作 / 家庭 / 媒体**，对应 /vol1 现有三个库（见 §0.5） |
| 投递入口 | **一个统一收件箱**（王震 2026-11-19 定：不设三个收件区）：`/vol1/1000/收件箱`，任何文件丢进去，App 判断归工作 / 家庭 / 媒体哪一类再归位；另支持**任意文件/目录选择处理**（Web 界面或命令行选定文件或目录，即自动做全量处理：盘点 → 分类 → 改名 → 打标签 → 归位） |
| 阈值 | 王震不懂，交由 muse 定：高置信 ≥0.85 自动执行（默认），0.60–0.85 进复核附建议，<0.60 进复核无建议 |
| 名字 | **NAS Curator（文件管家）**，muse 定 |
| 修库 | 软件做好后，再对 /vol1 全部文件做一次修库操作（放 P4，不在 P1 前单独做） |

### 0.5 /vol1 现状勘察（2026-11-19 实测）

| 目录 | 体积 | 结构 | 在新架构里的定位 |
| --- | --- | --- | --- |
| `/vol1/1000/工作文件/` | 41G | `1-王震 / 2-上海润心 / 归档 / 收件箱` | **工作库**；库内原有 `收件箱` 不再作为入口（保留目录不动） |
| `/vol1/1000/家庭文件/` | 45G | 按人分：`刘音 / 王子婴 / 王子轩 / 王现琦 / 王震 / 韩红` | **家庭库**；按人组织是既定结构，新分类须尊重「先按人、再按事」的层级 |
| `/vol1/1000/媒体库/` | 1.1T | `图书 / 影音 / _整理 / 照片 / 视频 / 音乐` | **媒体库**；库内原有 `_收件箱` 不再作为入口（保留目录不动）；注意除照片视频外还有图书、音乐，媒体引擎不得误伤这两类 |
| `/vol1/1000/下载/` | 202G | `Wangzhen-Mac/ 146G / 压缩包/ 37G / AI模型/ 20G / 夸克网盘/ 0` | **输入源，不是库**：`Wangzhen-Mac/` 是笔记本备份，同步方向为**只上传（Mac → NAS 单向）**，NAS 侧整理不会回写到 Mac，因此里面的文件**需要整理、判断应归工作 / 家庭 / 媒体哪一类**（2026-11-19 王震纠正）。`AI模型/` 是模型文件，不动；`压缩包/` 可日后单独处理 |
| `/vol1/1000/_统一分析报告/` | 4K | — | 报告区，不动 |
| `/vol1/1000/ocr-service/` | 0 | — | 空，不动 |

**由此定下的三条硬规则**：
1. 三大库的物理根目录不变：工作 → `工作文件/`、家庭 → `家庭文件/`、媒体 → `媒体库/`；新 App 只在库内整理，不新建顶层库目录。
2. **一个统一收件箱 + 任意选择处理**（2026-11-19 王震定：不设三个收件区）：收件箱只有一个，`/vol1/1000/收件箱`，任何文件丢进去，App 判断归工作 / 家庭 / 媒体哪一类再归位；另支持在 Web 界面或命令行任意选定文件或目录，即自动做全量处理（盘点 → 分类 → 改名 → 打标签 → 归位）。`下载/Wangzhen-Mac/`（笔记本备份，只上传）作为输入源之一，可整目录选中处理，也可定时扫描；其中 `muse/` 子目录（muse 工作文件夹）排除，`下载/AI模型/` 不动；`下载/压缩包/` 日后单独处理。原有的 `工作文件/收件箱`、`媒体库/_收件箱` 不再作为入口（保留目录不动，里面的文件可移入统一收件箱处理）。
3. 家庭库「按人分」的既定结构保留：家庭文件的第一级分类维度是人，第二级才是事项/类型；工作库第一级是业务线（王震个人 / 上海润心 / 归档），媒体库第一级是媒介类型（照片 / 视频 / 音乐 / 图书 / 影音）。

### 0.1 一句话

**NAS Curator**：一个跑在飞牛 NAS 上的文件管家软件，统一管理文档与媒体库——按规则自动分类存放、自动改名、自动打标签；高置信自动执行，低置信进复核队列；绝不删原件、绝不覆盖，全程可回滚。

### 0.2 解决的问题

| 现状痛点 | 本 App 的解法 |
| --- | --- |
| 两个技能是散的（workfiles + media），各一套触发、各一套配置 | 一个服务、一个 Web 界面、一个复核队列、一个设置页 |
| 只能靠 Marvis 对话 / 命令行触发，没有界面 | Web 界面：总览、复核队列、规则编辑、按标签/分类浏览、任务历史 |
| 配置散在 rules.json / config.json / llm.json 三处 | 配置集中进设置页 + 单一数据库，改规则不用改文件 |
| 只能按文件夹找文件 | 加一层标签体系（机构、年份、业务类型、人物/场景），同一文件可多标签，按标签检索 |
| 人工操作多 | 高置信自动执行（分类、改名、打标签、归位），人工只点低置信复核；定时自动扫统一收件箱 |

### 0.3 非目标（v1 不做）

- 不是图库服务器（不做 Immich/PhotoPrism 那种备份 + 时间线 + 地图浏览）；文件整理是主业，浏览只是辅助。
- 不做全文检索服务器（不建 Elasticsearch）；标签 + 分类 + 文件名检索够用，v2 再评估。
- 不做跨 NAS 同步；只管本机 /vol1、/vol2。
- 不替用户删文件：任何删除都只发生在用户在复核队列里明确点「删除」之后，且删前先移入隔离区。

### 0.4 继承资产（复用，不重写）

| 现有资产 | 在新架构里的位置 |
| --- | --- |
| workfiles-curator：curator.py（1,378 行）、llmkit / textkit / semkit / orgkit / entitykit、clean_profile.py、eval 脚本、rules.baijing-supply-v8.json | 文档分类引擎的核心，包成 `curator_core` 模块；判定链、内容抽取、防打散、回滚逻辑原样保留 |
| media-library-curator：curate.py（884 行）、config.json | 媒体分类引擎的核心，包成 `media_core` 模块；SigLIP + ChineseCLIP、dHash、投递目录流程原样保留 |
| 模型栈 | bge-m3（ollama-gpu :11500）、qwen3:4b（ollama-cpu :11436）、火山 Ark Plan/PAYG、OCR 服务（:8866）、SigLIP / ChineseCLIP 本地缓存 |
| 评测资产 | 152 条审计样本、eval 脚本、复核口径（目录名 ≠ 真值），继续作为回归基线 |

### 1.2 为什么这样分层

| 决策 | 理由 |
| --- | --- |
| API 服务与分类引擎分离（进程内模块，同一容器先行，接口预留拆分） | v1 单容器最简单；引擎是 CPU/模型密集型，日后可独立扩容或移到另一台机器（学 Immich 的微服务化），接口先留好 |
| 模型做成可选独立微服务 | 重模型闲置自动卸载（学 Immich 的 MODEL_TTL，默认 300 秒）；小模型跑 NAS CPU，大模型可指向 Mac/GPU 机器；App 本体留在 NAS 上不臃肿 |
| SQLite 单文件元数据 | NAS 场景够用：单机、无并发写入压力、备份就是拷一个文件；不引入 PostgreSQL/Redis（Paperless-ngx 那套太重，NAS 上没必要） |
| 前端轻量 | 服务端渲染 + 少量 JS（或预编译的极简 SPA），不引 React 重型构建；NAS 上跑得动、维护成本低 |

### 1.3 技术栈

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 后端 | Python 3.11+、FastAPI、Uvicorn | 与现有两个技能同语言，复用代码零翻译成本；FastAPI 自带 OpenAPI 文档 |
| 元数据 | SQLite（WAL 模式）+ SQLAlchemy Core（轻量，不用 ORM 重封装） | 单文件、易备份、NAS 够用 |
| 任务队列 | 内置：SQLite 队列表 + 后台 Worker 线程（v1）；预留 Celery/Redis 接口（v2） | v1 不引入 Redis，少一个容器 |
| 前端 | 服务端模板（Jinja2）+ HTMX 或极简 JS | 不搞前后端分离构建链；页面直出，NAS 上好维护 |
| 向量 | bge-m3（现有 ollama-gpu :11500） | 已有，不引新模型；预筛层与语义层共用 |
| 媒体视觉 | SigLIP + ChineseCLIP（现有本地缓存） | 已有，中文语境优先 CN-CLIP；视频 v1 先用抽帧 + 现有分类，Qwen-VL 细判放 v1.1 |
| OCR | 现有 ocr-service（:8866），RapidOCR 兜底 | 已有 |
| 打包 | Docker Compose（多架构 linux/amd64 + linux/arm64）→ fnpack → .fpk | 同一镜像可上 fnOS / TrueNAS / 群晖，只需各写一份薄元数据 |
| 凭据 | 环境变量 / fnOS 凭据注入，绝不进镜像、绝不进仓库 | llm.json 现含火山 key，App 化时必须迁出 |

## 2. 统一数据模型（SQLite）

### 2.1 表一览

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `files` | 全库文件登记（文档 + 媒体同一张表） | id、path（当前路径）、sha256、size、mtime、kind（document/media）、ext、status（active/review/quarantine）、created_at、updated_at |
| `file_text` | 文档正文抽取缓存 | file_id、text（前 N 字）、source（pdftotext/ocr/ooxml/eml…）、extracted_at |
| `file_media` | 媒体分析结果缓存 | file_id、dhash、phash、width、height、duration、blur、clip_scores（JSON）、captions |
| `file_emb` | 向量缓存 | file_id、model、vector（BLOB）、updated_at |
| `categories` | 统一分类体系（文档类目 + 媒体类目同一张表） | id、path（如 `01-合同与协议`、`照片/家庭与人物/人物合影`）、kind、keywords（JSON）、desc、samples（JSON）、exts（JSON）、parent_id |
| `entities` | 实体画像（机构 → 常归哪类） | name、category_id、count、ratio、updated_at |
| `tags` | 标签定义 | id、name、kind（entity/year/biztype/person/scene/custom）、color |
| `file_tags` | 文件—标签多对多 | file_id、tag_id、source（auto/manual）、confidence |
| `rules` | 规则集（单条 JSON 行，版本化） | id、name、version、payload（JSON，全量规则）、is_active、created_at |
| `plans` | 分类/整理计划（plan.csv 的结构化版） | id、library、status（draft/pending_review/approved/applying/done/rolled_back）、created_at、summary（JSON） |
| `plan_items` | 计划明细（每行一个文件动作） | plan_id、file_id、src_path、dst_path、new_name、category_id、confidence、reason、evidence、action（move/rename/tag/skip）、status |
| `operations` | 执行记录（apply 的映射表， rollback 的依据） | id、plan_id、src_path、dst_path、sha256、executed_at、rolled_back_at |
| `review_queue` | 复核队列（低置信、重复、模糊、待确认统一入口） | id、file_id、plan_id、kind（low_conf/dup/blur/ambiguous/shell）、payload（JSON）、status（pending/approved/rejected）、decided_by、decided_at |
| `jobs` | 任务历史（扫描、盘点、执行、索引重建） | id、kind、status、started_at、finished_at、log_path、summary（JSON） |

### 2.2 关键设计说明

- **文档与媒体同一张 `files` 表**：`kind` 区分，`file_text` 与 `file_media` 各挂一张扩展表。这样去重、复核、回滚、检索都不用分两套逻辑；这正是「统一」的核心。
- **分类与标签分离**：`categories` 是「文件放在哪个文件夹」（单归属，决定物理位置）；`tags` 是「文件贴哪些标签」（多归属，只影响检索，不决定位置）。一个文件一个分类、多个标签。
- **规则版本化**：`rules` 表每次改动产生新版本，`plans` 记录用的是哪个版本；复核时能看到「这条计划是按哪版规则算的」，改规则不污染历史计划。
- **操作即回滚依据**：`operations` 表就是现在的 `map_<日期>.tsv` 的结构化版；回滚 = 按 `operations` 逆序把文件移回去，逻辑与现有 `rollback` 子命令一致。
- **索引复用**：media 现有的 `hash_index.tsv`（sha256、size、path、dhash、ts）在迁移时一次性导入 `files` + `file_media`，不丢历史去重数据；workfiles 现有的正文缓存（`--cache` 目录的 cache.json）同样导入 `file_text`。

### 2.3 标签体系（v1）

| 标签种类 | 来源 | 示例 |
| --- | --- | --- |
| 业务类型 | 分类引擎：文件名业务类型词 / 正文关键词 | 合同、发票、申报表、周报、纪要、招标 |
| 机构（对方主体） | orgkit / entitykit：正文抽机构名 | 北京红橙天天健康科技有限公司、波士顿科学 |
| 本方主体 | learn 自动学习：跨类目高频出现者 | 华润（北京）医疗器械供应链管理有限公司 |
| 年份 | 文件名日期 / 邮件 Date 头 / EXIF 拍摄日期 / mtime 兜底 | 2026、2025 |
| 人物/场景（媒体） | SigLIP + ChineseCLIP 分类结果 | 人物合影、旅行风景、美食与咖啡 |
| 质量（媒体） | 模糊检测、曝光检测 | 模糊、曝光不足（v1.1，Sila 模式） |
| 自定义 | 用户在 Web 界面手动打 | 任意 |

标签生成规则：分类确定后，引擎按「分类 → 业务类型标签、实体 → 机构标签、日期 → 年份标签、媒体分类 → 场景标签」的固定映射自动打；用户可在复核时增删；`file_tags.source` 区分 auto/manual，auto 标签被用户删掉后记一条负反馈（进学习闭环，见 §3.4）。

## 3. 统一分类引擎

### 3.1 总流程（文档与媒体同一条管线）

```
扫描/投递
  → 登记 files（SHA256，查重）
  → 稳定等待（投递模式：mtime 距今 < settle_minutes 跳过）
  → 内容抽取（文档：textkit；媒体：视觉模型 + EXIF + 帧采样）
  → 预筛层（bge-m3 / CLIP 向量，明显的文件直接定类）  ← 新增，P1
  → 判定链（文档五层 / 媒体双模型 + 阈值）
  → 置信度路由：≥ auto_threshold 自动执行；< 阈值进复核队列
  → 标签生成（§2.3）
  → 生成计划（plan）→ 用户确认（高置信可自动确认）→ 执行（apply）
  → 写 operations → 可回滚
```

### 3.2 文档判定链（沿用 v3.1.1，加预筛）

```
0. 预筛层（新增）：bge-m3 向量，文件名 0.45 + 正文 0.55；
   相似度 ≥0.75 且与第二名差 ≥0.10 → 直接定类，不走 LLM。
   （目标：压掉大半 LLM 调用；阈值先按 0.75 跑，拿 152 条样本校准）
1. 实体画像：正文机构名命中 entities（该机构过去 60%+ 文件落某类）→ 定类
2. 语义向量：bge-m3，相似度 ≥0.62 或与第二名差 ≥0.05 → 定类
3. 文件名业务类型优先（v3.1.1）：文件名含合同/协议/申报表/发票/简历/周报/纪要/招标/中标/花名册/营业执照/授权书 → 以文件名定类
4. 模型兜底：仍判不准的批量送模型（一次 6–8 条，并发 2），few-shot 样例
5. 无正文不猜：正文 <20 字且文件名为哈希/编号/IMG 类 → 直接待确认
6. 低置信：以上都不成立 → 复核队列，附证据片段
```

改动点（相对 v3.1.1）只有两处：加第 0 层预筛；第 6 层从 `99-待确认` 文件夹改为进 `review_queue` 表（Web 里点，逻辑相同）。

### 3.3 媒体判定链（沿用 media-library-curator，补视频）

```
1. 解码失败 → 复核队列（待确认）
2. SHA256 命中索引 → 疑似重复 → 复核队列
3. dHash 近重复（汉明距离 ≤5）→ 疑似重复 → 复核队列
4. 模糊检测（blur < 50）→ 复核队列（模糊）
5. 内容分类：SigLIP 判场景 + ChineseCLIP 判中文界面/截图/票据；
   白底占比 ≥0.45 且截图/文档得分高 → 截图/文档；
   top1−top2 < 0.12 或 top1 < 0.35 → 复核队列（待确认）
6. 视频（v1）：抽帧（首帧 + 每 10 秒一帧，上限 6 帧）走同一套图片分类，
   取众数；音频不做判定（v1.1 再加 Whisper / librosa）
7. 否则按分类归档，置信度写进 plan_items
```

v1.1 再补（不进 v1）：Qwen-VL 逐帧细判 + Whisper 音频 + 模糊/曝光质量筛查（Sila 模式）。

### 3.4 学习闭环（Paperless-ngx 模式，v1 打底、v1.1 闭环）

- **v1 打底**：复核队列里的每一次人工裁定（批准/改类/删标签）都写进 `review_queue.decided_*` + 一条反馈记录；`learn` 命令能读这些记录，重新生成实体画像与每类 samples（复用现有 clean_profile.py + learn 逻辑）。
- **v1.1 闭环**：反馈自动回写——被纠正过的（文件特征 → 正确类目）样本进入向量库，下次同类文件走预筛层即高置信；实体画像的 count/ratio 随复核实时更新，不用手动跑 learn。
- **评测口径不变**：继续用 152 条样本 +「目录名 ≠ 真值」的复核口径；先修库（11 条错放 + 质量标准类归属）再谈模型，顺序不倒。

### 3.5 防打散与隔离（沿用，不变）

- 程序/工程目录（`.git` / `node_modules` / `package.json` / `CMakeLists.txt` / `.exe`）整目录搬，不拆；`--protect` 指定目录整体保留。
- 同名主件（合同.docx / 合同.pdf）合并同处。
- 敏感文件（密码 / 账号 / 身份证 / 护照 / 银行卡 / token / key）独立隔离，不进业务库，不打印内容。
- 空壳（<2KB eml/msg）、加密壳、损坏压缩包、云同步加密壳进隔离区，按 A–E 分组等用户指令。

### 4.2 关键交互

- **复核是主界面**：日常打开 App 首先看到的就是复核队列有几条待点；点完即空，符合「减少人工操作」的目标。
- **计划先行**：任何批量移动都先出计划（dry-run），列清「移动多少、改名多少、隔离多少、可回收多少」，确认后才执行；高置信且开自动执行时，计划自动确认（阈值在设置里可调，默认 0.85）。
- **一键回滚**：每次执行生成一条 operations 记录，详情页点「回滚」即按映射逆序移回；回滚本身也记一条操作，可再反悔。
- **解释**：每个文件的分类都附依据（`reason` + `evidence` 片段），点开即看「为什么归到这里」，沿用现有 explain 能力。

## 5. 自动化与调度

### 5.1 三种触发方式（王震 2026-11-19 定：一个收件箱 + 任意选择处理）

| 方式 | 适用 | 做法 |
| --- | --- | --- |
| 统一收件箱 | 日常新增文件（主入口） | 只有一个收件箱：`/vol1/1000/收件箱`。任何文件丢进去 → 每 30 分钟扫一次 → 稳定等待 3 分钟 → App 判断归工作 / 家庭 / 媒体哪一类 → 自动分类、改名、打标签、归位；无文件秒退不加载模型。用户不用事先判断文件属于哪个库 |
| 任意选择处理 | 任意文件或目录 | Web 界面或命令行选定一个文件或多个文件、一个目录 → 即自动做全量处理（盘点 → 分类 → 改名 → 打标签 → 归位）。适用：`下载/Wangzhen-Mac/` 整目录处理、某个历史文件夹、刚拷进来的内容 |
| 定时扫描 | 输入源增量、整库 | `下载/Wangzhen-Mac/` 定时扫描新增文件并归位；整库增量扫描每日 03:00；整库全量（P4 修库）手动发起 |

### 5.2 自动执行的分寸

| 置信度 | 动作 |
| --- | --- |
| ≥ auto_threshold（默认 0.85，可调） | 自动执行：分类、改名、打标签、归位；记 operations，可回滚 |
| 0.60–0.85 | 进复核队列，但附建议分类与依据，用户一点即过 |
| < 0.60 或无正文/解码失败/疑似重复/模糊 | 进复核队列，无建议或建议置信度封顶 0.45，只作参考 |

### 5.3 定时任务（v1）

- 统一收件箱扫描：每 30 分钟（media 现有节奏，沿用）。
- 整库增量扫描：每日 03:00（只扫新增/改动，靠 mtime + size 比对，不重扫全库）。
- 索引健康检查：每周一次（SHA256 抽查 + 孤儿记录清理）。
- 任务历史全进 `jobs` 表，失败即留日志、不静默丢。

## 6. 安全与回滚（铁律，原样保留）

1. **绝不物理删除**：重复件进隔离区 / 复核队列，用户明确点删除后才删，且删前先移入隔离区留底。
2. **不覆盖**：目标同名加 `__n`、`__n+1`。
3. **移动用 `mv`**，不 `cp`+`rm`，避免中途重复占用。
4. **三件套**：每次执行同时产出映射表（`operations` 表 + 导出 TSV）、回滚脚本、执行报告，缺一不可。
5. **移动后 `chown 1000:1000`**，保证 NAS 侧可读写。
6. **不新建用户级顶层目录**；临时产物只写工作区。
7. **改动前必须先给方案并拿到确认**；未确认只做只读盘点（整库整理模式）。统一收件箱模式的高置信自动执行是例外，但阈值与开关在设置页，用户可随时关。
8. **敏感文件独立隔离**，不打印内容。
