# workfiles-curator 分析：改进空间、媒体库统一与飞牛 App 方案

2026-11-19 · 针对 NAS 上 workfiles-curator v3.1.1 与 media-library-curator 的实测分析 + GitHub 同类项目调研

## 结论先行

1. **workfiles-curator 本体已经很扎实**。四阶段流程（只读盘点 → 出方案等确认 → 可回滚执行 → 复核）、五层判定链、不删原件、同名加 `__n`、映射表 + 回滚脚本，安全底线做得到位。GitHub 上没有「既原地整理文件夹、又按业务实体画像、又带回滚」的现成竞品，你的五层链 + 回滚已是较完整的形态。
2. **媒体库整理你其实已经有了**。NAS 上除了 workfiles-curator，还有一个 `media-library-curator`（11 月 8 日建，已在跑）：照片/视频走投递目录，SHA256 精确去重 + dHash 近重复 + SigLIP + ChineseCLIP 双模型内容分类，15 个分类，每 30 分钟自动扫一次。workfiles-curator 的 SKILL.md 也写了「媒体照片视频请用 media-library-curator」，两个技能本来就是分工的。
3. **真正的缺口不是「缺媒体能力」，而是「两个技能是散的」**。没有统一入口、没有 Web 界面、配置散在各处（rules.json、config.json、llm.json），只能在 Marvis 里靠对话触发。**把两者合成一个飞牛 App，就是差异点本身**——调研确认目前没有「文档 + 媒体统一整理、同一套复核/回滚、跑在 NAS 上」的 App。
4. **做成飞牛 App 的路径是通的**：Docker-first（多架构镜像）→ fnpack 打包成 .fpk → 先用 appcenter-cli / 手动安装自用。开发手册直接用 fn-fpk skill，模板抄 carethink11/fnos-apps 的 Docker 模式。

## 二、workfiles-curator 改进空间（按优先级）

### P0：先修库，再谈模型

SKILL.md §10 自己下的结论就是答案：当前瓶颈是库本身的错放和评测口径，不是模型能力。再换更强模型收益有限。建议：

- 把 152 条审计里那 11 条「库内错放」先纠正（个税申报表在「供应商与采购」、产品手册在「人事」这类），再跑评测才有意义。
- 给「质量标准类」一个明确归属：`螺钉验收标准`这类采购验收文件在 14 类体系里没有专门位置，实测同一文件先后被判 `04-供应商与采购`（0.75）、`14-工具与其他`（0.55），不稳定。业务上定一个归属（推荐 `06-库存与物流`或 `04`），写进该类 `desc` 即可。

### P1：加一层本地编码器预筛，压掉大半 LLM 调用

这是 laya-file-organizer（GitHub 新项目，ModernBERT 编码器，纯 CPU 约 35ms/文件）验证过的模式：在五层链之前，用现有 bge-m3 对「明显」的文件直接定类，只有模糊的才走 LLM。curator 不用引新模型就能做（bge-m3 已在里面），可大幅削减火山调用量与耗时。

### P2：把复核纠错反馈回分类器（学习闭环）

这是 Paperless-ngx（47k stars，文档归档标杆）最值得抄的一点：从用户复核纠错中在线学习分类器。curator 已有 learn/audit 与 152 条审计数据，缺的就是闭环——把复核结果回写为实体画像/向量样本，下次同类文件自动走高置信度通道。

### P3：隐私分级（可选模式）

llm-file-organizer 的做法：只把文件名发给 AI，不发文件内容；模糊文件才问 LLM。可以作为 curator 的一个可选模式，对敏感库（合同、财务）尤其有用。

### P4：中文分类命名习惯

FolderFox（中文社区项目，DeepSeek 驱动）的做法值得参考：分类命名贴合中文习惯（如「2024Q4 项目报告」→「项目文档/2024Q4」）、「按文件名前缀归档」模式对中文归档文件很实用。

### 不建议做的

- **不要直接照搬 Paperless-ngx 整套**：它是「归档系统」（文档吸入自己的库内管理），curator 是「原地整理文件夹」，定位不同；它重（4–6 容器），不宜照搬。但它的分类思想、OCR 管线、学习闭环是行业标准答案，值得借鉴。
- **不要为换模型而换模型**：SKILL.md 已写明，再换更强模型收益有限。

## 三、media-library-curator 现状与缺口

### 已有的能力（别重复造轮子）

| 能力 | 现状 |
| --- | --- |
| 位置 | 同目录下 `media-library-curator/`，curate.py 884 行 + config.json + run.sh |
| 流程 | 投递目录（`/vol1/1000/媒体库/_收件箱`）→ 稳定等待 3 分钟 → 去重 → 内容分类 → 归档移动 → 更新索引 → 出报告 |
| 去重 | SHA256 精确去重 + 64 位 dHash 近重复（汉明距离 ≤5 判疑似重复），实测 127 张随机照片两两距离均 >8，误报风险低 |
| 内容分类 | SigLIP（ViT-B-16）判场景 + ChineseCLIP（OFa-Sys）判中文界面/截图/票据；白底占比 ≥0.45 且截图/文档得分高时优先判截图/文档 |
| 分类体系 | 照片 12 类 + 视频 6 类 + 3 个复核区（待确认/模糊/疑似重复） |
| 模型 | 全部本地缓存，`HF_HUB_OFFLINE=1`，无网也能跑 |
| 自动执行 | 每 30 分钟扫一次投递目录，无文件秒退不加载模型 |
| 安全 | 不删除、不覆盖、只处理投递目录、移动后 chown 1000:1000 |

**注意**：媒体技能已经在用 ChineseCLIP（不是英文偏的 OpenAI CLIP），也已经有 dHash 近重复——GitHub 调研里「用 CN-CLIP」「加感知哈希」这两条建议，你的媒体技能已经做到了，不用再补。

### 真正的缺口

| 缺口 | 说明 | 参考 |
| --- | --- | --- |
| 视频内容理解较浅 | 目前视频分类主要靠模型打分；vsort（GitHub 上唯一按内容把视频分进文件夹的项目）的做法是 Qwen3-VL 逐帧 + 视频级判定 + librosa 音频特征（节奏/人声/音色），251 视频验证集约 87% 自动归档、准确率约 90% | vsort：github.com/76mpt/Video-Analysis-and-Categories |
| 质量筛查 | Sila 的做法：VLM 打标签（LLaVA）+ 模糊/曝光质量检测，是整理媒体库时「先筛掉废片」的实用能力 | Sila：github.com/amitjoshi9627/Sila |
| ML 微服务化 | Immich 的架构经验：ML 是独立微服务，`MODEL_TTL`（默认 300 秒）闲置自动卸载模型——重模型可放另一台有 GPU 的机器或按需加载，App 本体留在 NAS 上 | Immich：github.com/immich-app/immich（约 115.6k stars） |
| 没有 Web 界面 | 和 workfiles-curator 一样，只能靠对话/命令行触发，没有复核界面 | 见第五节 |

### B. 媒体库整理类

**关键结论**：市面上几乎所有媒体库工具都是「建索引 + 搜索」（文件留在原地、靠向量/标签检索），而不是「按内容重命名并移动文件夹」。真正按内容把视频分进文件夹的只有 vsort 一家。也就是说，media-library-curator（按内容理解后生成整理计划、人工复核、再移动 + 回滚）在这个方向上没有直接竞品，形态上更接近 workfiles-curator 的延伸，而非 Immich/PhotoPrism 的翻版。

| 项目 | 星数 | 一句话 | 最值得抄的点 |
| --- | --- | --- | --- |
| Immich | 约 115.6k | 照片/视频自托管事实标准：CLIP 智能搜索 + InsightFace 人脸聚类 + OCR + 去重 | ML 独立微服务 + MODEL_TTL 懒卸载；多语言 CLIP |
| PhotoPrism | 约 40.3k | 单容器、省资源的档案派：NASNet 图像标签 + rules.yml 阈值表 | rules.yml 阈值表；约 3GB 内存、无 GPU 可跑 |
| Lap | 4,144 | 离线优先、文件夹优先的桌面管理器：CLIP + InsightFace 全本地跑 | ONNX 化 CLIP + InsightFace 本地推理栈；文件夹优先 |
| Sila | 未核实 | 本地 AI 媒体工作室：LLaVA 场景描述 + CLIP + MiniLM 三模态混合检索 + Whisper | VLM 打标签 + 质量检测（模糊/曝光）；RRF 多路检索融合 |
| vsort | 未核实（2026-11 新项目） | 唯一按内容把视频分进文件夹：CLIP/SigLIP 2 + Qwen3-VL 逐帧 + librosa 音频 | 与 curator 安全哲学完全同构（复核队列 + dry-run + 撤销）；视频侧最直接参考 |
| CN-CLIP | — | 阿里巴巴达摩院中文 CLIP，约 2 亿中文图文对训练 | 中文语境下优先用 CN-CLIP（你的媒体技能已在用） |

内容理解技术栈已收敛：**CLIP/CN-CLIP 向量（粗筛/检索）+ VLM 打标签（LLaVA / Qwen-VL，细判）+ 人脸聚类（InsightFace）+ 视频抽帧 + Whisper 音频**。

## 五、做成飞牛 App 的路径

### 推荐路线：Docker-first → .fpk → 自用 → 分发

```
curator + media 能力打成一个多架构 Docker 镜像
  （Python + ONNX/CN-CLIP 小模型）
    → docker-compose（挂载 /vol1、/vol2 只读 + 专用输出目录）
      → fnpack 打包成 .fpk（manifest 里 platform=all）
        → 先用 appcenter-cli / 手动安装自用
          → 再考虑进 carethink11/fnos-apps 或 FnDepot 分发
```

### 关键设计决策

| 决策 | 建议 | 理由 |
| --- | --- | --- |
| 形态 | Docker Compose（推荐），`platform=all` | fnOS 官方两种形态（Native 与 Docker）中 Docker 最省事；同一镜像可同时上 fnOS（.fpk）、TrueNAS（Custom App）、群晖/QNAP（Container Manager），只需各写一份薄薄的商店元数据 |
| Web 界面 | 必须做，是 App 的必需品 | 把 curator.py 现有的 plan/apply/rollback/explain 子命令包一层 Web UI（计划 → 复核 → 执行 → 回滚），形态参考 LazyBones/LazyFlowAI；这一步与「做成 fnOS App」是同一件事，不用做两遍 |
| 设置界面 | fnOS 向导 UI + Web 复核页 | 规则、路径、LLM 端点、复核队列，都进设置页；配置不要再散在 rules.json/config.json/llm.json 三个文件里 |
| 模型层 | ML 做成独立微服务，学 Immich 的 MODEL_TTL | 重模型闲置自动卸载；小模型跑 NAS CPU，大模型可指向 Mac/GPU 机器；App 本体留在 NAS 上 |
| 凭据 | 绝不能进镜像 | llm.json 现在含火山 API key（600 权限）；做成 App 时 key 必须走 fnOS 的凭据/环境变量注入，不要打进镜像、不要写进仓库 |
| 路径 | 全部可配置 | 现在硬编码了 `/vol1/1000/...`、`/vol2/@appdata/marvis-app/...` 等 NAS 绝对路径；App 化时一律改成设置项 + 卷挂载 |
| sudo | 消除对 sudo -n 的依赖 | 现在读 /vol1 要加 `sudo -n`；App 以容器方式运行时通过卷挂载 + 正确的 UID/GID 解决，不要在容器里 sudo |
| 分发 | 先自用，再考虑上架 | 官方上架需申请（飞书表单/商务联系），无公开开发者门户；不上官方商店时 FnDepot 是最现成的分发渠道 |

### fnOS 打包要点（官方）

- manifest（无扩展名，key=value）：`appname`（全局唯一）、`version`、`display_name`、`source=thirdparty`、`platform`（`x86` / `arm` / `all`，Docker 应用常用 `all`）、`checksum`（MD5，fnpack 自动生成）
- 项目结构：manifest + ICON.PNG（64×64，必需）+ 生命周期脚本 + 向导 UI（wizard）+ CGI 反向代理 + 统一网关注册 + 中间件 + `@trimjs/web-app` 前端 SDK + 飞牛 Open API
- 安装：`appcenter-cli install-fpk myapp.fpk`；应用中心 → 设置 → 手动安装可上传 .fpk（2025-11 起官方开放离线安装）
- 系统底子：fnOS 为 Debian 系、内核 6.12.18+，x86_64 与 ARM64 双架构；运行时数据在 `/vol{卷}/@appdata/[appname]`，用户数据在 `/vol{卷}/@apphome/[appname]`

## 六、建议的下一步（按顺序）

1. **先修库**：把 152 条审计里 11 条「库内错放」纠正 + 给「质量标准类」定归属，再跑评测。这是零成本、收益最大的事。
2. **加预筛层**：用现有 bge-m3 在五层链前加本地编码器预筛，压 LLM 调用量。
3. **定 App 形态**：确认要不要把 workfiles-curator + media-library-curator 合成一个 App（推荐合成，差异点就在「统一」），还是先只把 workfiles 做成 App、媒体保持独立。
4. **搭 Web 复核页**：这是 App 化的核心工作量，形态参考 LazyBones/LazyFlowAI。
5. **Docker 化 + fnpack 打包**：按 carethink11/fnos-apps 的 Docker 模式模板，用 fn-fpk skill 作开发手册，先在 NAS 上用 appcenter-cli 自用安装验证。
