## 0. 一句话结论

**卡点是"自动执行门槛 0.85"与两种分类器的实际分数分布不匹配**，不是分类速度，也不是守卫本身：

- 文档走 LLM，实测 370 条 LLM 判定**最高分就是 0.80**，一条到不了 0.85 → `--llm` 模式下文档永远无法自动执行。
- 媒体是 12 类 softmax，实测 349 条中位数 0.58、p90 0.78、最高 0.85 → 大部分永远够不到 0.85。

当前 1,151 条待复核里，按现行 0.85 门槛只有 **3 条**能自动；把门槛改成"媒体 0.65 / 文档 0.75"后，同样这批里 **385 条（33%）** 可自动。**这一个改动就是最大杠杆。**

另外发现一个独立但同等重要的问题：**批量批准是空转**（点了只改状态、不搬文件），因为复核项的建议目标被主动清空成空字符串。

## 2. 根因（逐条对应代码）

### 2.1 【主因】自动执行门槛 0.85 不适配 LLM 与媒体

`common/routing.py:238 is_auto_apply_eligible`

```python
def is_auto_apply_eligible(item, threshold=0.85):
    ...
    return _conf_of(it) >= threshold     # 单一全局门槛
```

调用方（三处，口径一致）都传 `libraries.json` 的 `thresholds.auto`：

- `curator.py:1002`（CLI `_apply_items`，watcher 走这条）
- `api/jobs.py:155`（Web `_run_auto_apply`）
- `config/libraries.json:77` `"auto": 0.85`

0.85 是为文档**规则分**（12 分→0.9、8 分→0.85、min_score→0.7）设计的。但：

- `--llm` 模式下文档实际由 LLM 给分，`curator_core/engine.py:_map_confidence` 对 `llm:` 前缀直接取返回值，实测上限 0.80。
- 媒体 `media_core/engine.py:437` 用 `confidence = float(s1)`，s1 是 12 类 softmax 的 top1，天然低。

**结果：两种分类器的高质量结论都卡在 0.85 门外。**

### 2.2 【主因·交互】守卫在阈值之前执行，且用同一个全局阈值

`common/routing.py:261 apply_path_prior_guard`，由 `curator.py:175 _apply_path_guard` 调用：

```python
threshold = ((cfg or {}).get("thresholds") or {}).get("auto", 0.85)   # 同一个全局值
items, info = RT.apply_path_prior_guard(items, roots, threshold)
```

守卫把 `conf < 0.85` 且跨顶层的项转 review，并**清空 dst、压到 0.45**。

关键实测：守卫拦下的 735 条里，**原分 ≥0.85 的只有 3 条**。所以：
- 单纯去掉守卫，几乎放不出文件（还是被 0.85 拦）；
- 单纯改门槛，也不够（守卫先用 0.85 把跨顶层的全转 review 了）。

**两者必须一起改。**

### 2.3 守卫对"收件箱→库"也生效，等于让收件箱永远出不了件

收件箱（`/vol1/1000/收件箱`）按 `config/libraries.json` 定位是"唯一投递入口，丢进去由系统判断归哪个库"。对收件箱文件而言，"移到工作/家庭/媒体"是**正常且唯一**的去向，不是"危险跨库迁移"。守卫不区分，全部拦下。

实测佐证：1,151 条里 1,104 条 src 在 `/vol1/1000/收件箱/home`，`current_top` 全是"收件箱"。

### 2.4 【独立问题】批量批准空转：建议目标被清成空字符串

三处主动清空 `dst`：

| 位置 | 代码 |
|---|---|
| `curator_core/engine.py:611` | `if is_review: dst = ""` |
| `media_core/engine.py:164` `_review_item()` | `base.update({"dst": "", ...})` |
| `common/routing.py:288` 守卫 | `it["dst"] = ""` |

于是 `_store_plan`（`curator.py:500`）写进 payload 的 `suggested_dst` 恒为 `""`。

而批量裁定：

```python
# api/review.py:368
@router.post("/bulk")
def bulk(body: BulkBody, ...):
    for rid in body.ids:
        decide_one(conn, rid, body.decision)     # ← 不传 body

# api/review.py:288
dst = (body.suggested_dst if body and body.suggested_dst
       else payload.get("suggested_dst") or "")
if not src or not dst:
    return {"ok": True, "id": review_id, "moved": False,
            "note": "无 suggested_dst 或源路径，仅更新状态"}
```

**批量批准 100% 落到"仅更新状态"分支。** 前端 `review.html:215` 的 `bulk()` 也确实只发 `{ids, decision}`。

单条批准同样中招：`categoryOptions()`（`review.html:36`）默认选中 `current_top`（对收件箱文件是"收件箱"），而 `_recompute_dst_for_top` 只处理 work/family/media，"收件箱"无分支 → dst 仍空 → 不搬。

### 2.5 复核项把 0.84 显示成 0.45，用户误判"系统不准"

守卫压到 0.45 后，界面显示 0.45。用户看到"只有 45% 把握"，实际是 0.84。这让用户更不信系统、更愿自己动手。

### 2.6 `review_suggest` 是死配置

`thresholds.review_suggest=0.60` 只在 `api/deps.py:124` 设默认值、在 `rules.html`/`setup.html` 回显，**没有任何分类或队列逻辑读它**。

### 2.7 复核页丢二级类目

`_recompute_dst_for_top`（`api/review.py:59`）无 suggested_dst 时一律落到：
工作 → `工作/归档/`、家庭 → `家庭/<人>/`、媒体 → `媒体/照片|视频/`。
分类器已知的二级类目（"供应商与采购""儿童成长"）全丢。

## 3. 改法（按性价比排序）

### 3.1 【最高优先·一个改动解决 33%】分模态阈值，并同步传给守卫

**第一步：配置**（`config/libraries.json`）

```json
"thresholds": {
  "auto": 0.85,
  "auto_doc_llm": 0.75,
  "auto_media": 0.65,
  "auto_media_margin": 0.15,
  "review_suggest": 0.60
}
```

**第二步：统一取阈值的函数**（`common/routing.py` 新增，供守卫与 auto 资格共用）

```python
def auto_threshold_for(item, cfg_thresholds):
    """按项取自动执行门槛。文档 LLM / 媒体 各有专属阈值。"""
    th = cfg_thresholds or {}
    reason = (item.get("reason") or "")
    if reason.startswith("llm:"):
        return float(th.get("auto_doc_llm", 0.75))
    if item.get("kind") == "media" or _is_media_ext(item.get("ext")):
        return float(th.get("auto_media", 0.65))
    return float(th.get("auto", 0.85))
```

**第三步：`is_auto_apply_eligible` 改为按项取阈值**（保留单参调用兼容）

```python
def is_auto_apply_eligible(item, threshold=None, thresholds=None):
    it = item or {}
    if it.get("action") not in ("move", "rename"): return False
    if it.get("kind") == "unit" or it.get("ext") == "(目录)": return False
    thr = threshold if threshold is not None else auto_threshold_for(it, thresholds)
    if not _conf_of(it) >= thr:
        return False
    # 媒体另加 margin 约束（evidence 里有 top2 分数时校验）
    if it.get("kind") == "media":
        m = _media_margin(it)          # 从 evidence "A 0.72 / B 0.10" 解析
        if m is not None and m < float((thresholds or {}).get("auto_media_margin", 0.15)):
            return False
    return True
```

**第四步：守卫按项取阈值**（`apply_path_prior_guard` 内部改调 `auto_threshold_for`，或由调用方传 `thresholds` 字典）。

**第五步：收件箱→库豁免"危险跨库"判定**

```python
src_top = library_top(src, roots)
dst_top = library_top(dst, roots)
# 收件箱/输入源 → 三库 属于正常归位，不按"危险跨库"处理
if src_top in ("inbox", "mac-backup") and dst_top in ("work", "family", "media"):
    if conf < auto_threshold_for(it, thresholds):   # 仍按分模态门槛把住
        -> 转 review，但保留 dst（见 3.2），不清空
    else:
        -> 放行（保持 move）
```

**收益**：当前这批 1,151 条中 385 条（33%）转为自动。后续新文件同样按新门槛走。

**风险控制**：前 200 条自动执行后抽 20 条人工核，稳定后再全量；operations 表可按 batch 回滚。

### 3.2 【最高优先·独立】保留建议目标，让批量批准真的能搬

1. **引擎不要再清空 dst**：`curator_core/engine.py:611`、`media_core/engine.py:164`、守卫三处，review 项保留 `dst` 作为建议。
2. **payload 增加原始分**：`suggested_dst`、`confidence_original`。
3. **`/bulk` 支持 category 并透传**：

```python
class BulkBody(BaseModel):
    ids: list[int]
    decision: str
    category: str | None = None

def bulk(body: BulkBody, conn=Depends(get_db)):
    for rid in body.ids:
        decide_one(conn, rid, body.decision,
                   DecideBody(decision=body.decision, category=body.category))
```

4. **前端**：加"按建议批准"按钮（不传 category，走 payload.suggested_dst）；`categoryOptions` 默认选中 suggested_dst 的顶层；显示 `confidence_original`。

**收益**：一次点击清空一整个文件夹。`收件箱/home` 的 1,103 条可分几次批完。

### 3.3 【高】让 `review_suggest` 生效，队列自动二分

`confidence_original >= review_suggest` → 标"建议批准"（绿色，可整批）；
`< review_suggest` → 标"需人工判断"（黄色）。

这样 7,151 条一眼分成"可整批"和"要逐条"两堆。

### 3.4 【高】分流"不该占人工队列"的杂项

`unreadable:empty` 79 条、`unsupported_ext` 12 条、`no-text` 16 条、`blurry` 4 条 = **111 条**。它们不是分类失败，是文件本身没法判。建议 `review_queue.kind` 细分（`unreadable`/`unsupported`/`blurry`），Web 默认过滤，或整批移到 `_待处理/`。

### 3.5 【中】`收件箱/home` 当一次性批任务跑

1,103 个文件堆在一个目录（11-26 华为云/百度批量下载）。用
`curator.py process --root /vol1/1000/收件箱/home --apply` 单独跑，不受 inbox 的 `max_files_per_run=300` 限制。

⚠️ **注意 `_ReviewSkipper` 的坑**（`curator.py:839`）：已进复核且未改动的文件会被跳过，所以**改完阈值后这批不会自动重分类**，必须显式重跑（清 fingerprint 或提供 reclassify 接口）。见 §4.3-4。

### 3.6 【中】dup 1,581 条可整批批准

dup 批准语义是"移入 `06-重复待确认区`，不删除"，风险低。先跑 dry-run 看候选：
`common/dup_delete.py::delete_exact_dup_copies(dry_run=True)`，只报数不删。

### 3.7 【可选·收益最大，但改目录结构】EXIF 日期 + 时间轴归档

**现状**：`common/tags.py::extract_year` 只用文件名/正文/mtime，**完全没读 EXIF**。手机照片靠 mtime 判年份会失真（拷贝/下载重置 mtime）。

**建议**：照片/视频读 `DateTimeOriginal` → 按年/月归档：
```
媒体库/照片/2024/2024-03/xxx.jpg    ← 目录由 EXIF 决定，100% 确定
```
内容分类（儿童成长/自拍…）只写 `file_tags` 供检索，不影响归位。

**收益**：媒体归位从"12 类 softmax 必须过门槛"变成"EXIF 有日期即 100% 自动"，理论上消除绝大部分媒体复核。
**代价**：改变现有 `照片/家庭与人物/儿童成长/` 结构。**必须王震先定目录结构。**

## 4. 全自动路线图

### 4.1 四层闸门设计

| 层 | 条件 | 动作 | 人工 |
|---|---|---|---|
| L0 确定性 | SHA256 重复 / EXIF 日期 / 文件类型明确（安装包、压缩包） | 直接归位或移副本 | 0 |
| L1 高置信 | 文档 LLM ≥0.75；媒体 SigLIP ≥0.65 且 margin ≥0.15 | 自动归位 | 0（抽检） |
| L2 建议复核 | `review_suggest` ≤ 分 < 门槛，**带建议目标** | "建议批准"队列，可整包批 | 1 次点击/包 |
| L3 人工判断 | 真没把握 / 冲突 / 不可读 | "需判断"队列 | 逐条 |

修好 §3.1~3.3 后，L1 从几乎 0 提升到约 33%（当前队列口径），L2 有了建议目标可批量过，L3 只剩真难项。

### 4.2 落地顺序（每步可独立回滚）

1. **只读诊断**：`scripts/reevaluate_review.py --db ...`（dry-run，脚本已存在）。
2. **备份 DB**：`VACUUM INTO /data/backups/nas-curator.db.bak-<日期>`。
3. **改 §3.1 + §3.2**（阈值 + 守卫 + 批量目标），部署后在 `收件箱/home` dry-run 看建议。
4. **小批量 apply 50 条**，人工核 10 条，`rollback` 验证可回滚。
5. **改 §3.3 + §3.4**，再跑 200 条抽样。
6. **全量清队列**：dup 整批批；`收件箱/home` 按建议批准。
7. **长期**：§3.7 EXIF 改造（需王震先定结构）。

### 4.3 防跑飞护栏（必须保留）

1. **全部可回滚**：operations + rollback 已有；新阈值批次单独打 `batch_id`，一键回滚。
2. **抽检**：每自动执行 200 条，随机抽 5% 进"待抽检"，发现问题整批回滚 + 调阈值。
3. **阈值热更新**：确认 API 侧 `_run_auto_apply` 每轮读 cfg（现在 CLI 是每轮读，API 需确认）。
4. **`_ReviewSkipper` 的坑**：改阈值后，已进复核的文件因指纹一致被跳过，**不会重分类**。必须提供 `POST /api/review/reclassify`（按 id / 按文件夹重跑），或改阈值时清空受影响 pending 项的指纹。
5. **源文件不存在**（已见 7 条）自动清出队列。
6. **不自动删原件**：dup 只移 holding 区；`dup_delete` 保持三重验证。

### 4.4 预期效果（保守）

| 项 | 现状 | 改造后 |
|---|---|---|
| 待复核 | 7,151 | ~300–500（仅 L3） |
| 人工操作 | 每天 6 条 | 每包 1 次点击 + 每周抽检 |
| `收件箱/home` 1,103 条 | 积压 2 天+ | 一次批处理清空 |

## 5. 附带发现

1. **`/api/review` 一次返回全量**：1,151 条 = 620KB+，7,151 条估 4MB+，实测在 620KB 处中断。建议分页（`/review` 与 `/review/folders` 都要）。
2. **`review_suggest` 死配置**（§2.6）。
3. **置信度被压 0.45**，前端应显示原值（§2.5）。
4. **`_ReviewSkipper` 与改阈值的冲突**（§4.3-4）。
5. **VLM 脚本（vlm_reclassify / vlm_apply / year_*）不在仓库里**——NAS 上跑的是仓库外脚本。建议纳入仓库，否则回归测试与维护无从谈起。
6. **`unreadable:empty` 79 条**：确认是真空文件还是 `/vol1/1000` 权限（mode 000 + trimacl）导致读不到。

## 6. 需要王震拍板

1. **是否接受分模态阈值**（媒体 0.65、LLM 文档 0.75）——放宽自动执行，有回滚兜底。

3. **谁执行**：muse 在 NAS 直接改，还是走"一键升级 watcher"（`api/upgrade.py`）。
