**关键机制（决定 dry-run 做法）**：
- `plan_files` 的 `deep` 参数默认 False；CLI 从不传 deep；auto 模式只下钻透明目录。实测 auto 下工作文件 14,427 文件只产出 3 项。
- `scan_units` 规则：冻结目录（DEFAULT_FROZEN：归档、已整理、系统、备份…）一律跳过；其余非单元目录保持原样；**单元目录（project）整体搬、不拆散，单元内只抽样分类**。deep 模式把 max_depth 2→5 且下钻全部非冻结目录。冻结目录须以其本身为 --root 才能扫到。
- **因此 dry-run 的计划项数很小，但每项多半是一个整目录（数百至数千文件）**。计划项 ≠ 文件数；覆盖文件数须另计（见汇总脚本 `scripts/summarize_repair.py`，单元项按其 src 目录下实际文件数计）。
- 单元项置信度 0.4 但 auto_exempt=1（P1.1 修复：单元行豁免自动执行阈值，整目录搬是设计行为）；散文件按 ≥0.85 自动、<0.85 进复核。汇总分流口径与 apply 门控一致。

**各批规模（2026-11-19 实测）**：工作文件 14,427 文件 / 41G；家庭文件 2,896 文件 / 45G；媒体库 160,500 文件 / 1.1T；Wangzhen-Mac 116,725 文件 / 146G。合计约 294,548 文件。

### 4.3 风险点（dry-run 揭示）

1. **整目录搬的风险**：单元项一旦判错类目，整个项目文件夹（数百至数千文件）会被搬错地方。执行前必须逐项核对单元项的目标路径，尤其是置信度 0.4 的单元项（单元名即类目，置信度天生低、靠豁免自动执行）。
2. **家庭批复核量大**：2,003 项家庭计划里 1,982 项进复核（99%）。建议家庭批先只执行高置信项（48 项自动里家庭占 21 项），低置信项人工逐项过；王震一批（1,810 项）须带 LLM 重跑一次再审（97% 落默认类目 06-其他）。
3. **大文件/图书/音乐/AI模型/压缩包已排除**：按 guard 规则不动（媒体库图书/音乐不得误伤；下载/压缩包日后单独处理；下载/AI模型/排除；muse/ 子目录排除）。
4. **媒体批 61 小时**：跑完之前不要动媒体库；跑完后先审计划再执行。Mac 批已出计划（857 项），同样先审再执行。
5. **LLM 兜底很慢**：NAS 上 qwen3:8b（CPU）分类一个文件要几十秒，文件一多就成瓶颈（王震家庭目录一批跑了 47 分钟未完）。大批量修库建议只走预筛+语义，LLM 只对少数高价值文件开；或等火山 Ark key 填好走云端。llmkit 已关 thinking（`"thinking": {"type": "disabled"}`）、num_predict 有上限（80–700），慢是 CPU 算力问题，不是 thinking 漏关。
6. **两个 one-off 干跑容器与 App 共用 DB**：media/mac 计划写库时与监听器（每 30 分钟写 inbox 计划）并发写同一 SQLite（WAL + busy_timeout），目前未见锁错；若后续出现 database is locked，优先查此并发。
