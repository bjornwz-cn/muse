### 4.3 镜像构建：全量构建 stall，改走快速构建（等价性已核实）

全量构建（项目 Dockerfile）卡在 pip 安装层：`pip install` 进程 30 分钟
仅读 8MB（`read_bytes` 67 秒内零增长，wchan 为 poll 等待 socket），
当时正在下载 torch-2.15.0+cpu（209.5MB，download-r2.pytorch.org）。
根因是 Docker 层缓存失效：Dockerfile 的 `LABEL version` 行在 pip 层
之前，版本号一改即 bust 全部后续层缓存，0.1.5 全量构建须重装全部依赖
（0.1.4 构建时同样重装过，属已知代价；P7 §6.4 已记录“构建缓存观察”）。

改走的快路：以 `nas-curator:0.1.4` 为底，只复刻 Dockerfile 的 COPY
部分（源码 + VERSION + LABEL version=0.1.5），不改依赖、不改
ENV/ENTRYPOINT/HEALTHCHECK。等价性依据：`requirements-image.txt`
自 0.1.4（commit 5c317eb，torch 钉死）后未变（git log 核实），
依赖层与 0.1.4 完全相同；0.1.5 未删任何源码文件（只新增 3 个模块、
4 个测试文件——测试不进镜像），COPY 全量覆盖无残留。
快路构建两次（第一次的镜像不含 §7 的顶部版本号改动，第二次重打后
覆盖同一标签）：最终 `nas-curator:0.1.5` sha `5682fa4407ae`，
1.55GB，构建耗时约 7 秒。

遗留：`docker run --rm` 直接验镜像内容未成功——entrypoint 会先检查
挂载，`/vol1/1000` 未挂载时只打印两行即退出，未执行传入的命令；
镜像内容改由部署后的 live 容器验证（§4.2 全部通过）。
**全量构建 stall 的问题仍在**：下次 `requirements-image.txt` 变化
或 LABEL 之外的 Dockerfile 变化时，全量构建仍会重装依赖并可能再次
stall；届时可考虑把 LABEL 移到 Dockerfile 末尾（让 pip 层缓存
不受版本号影响），或把 torch 轮子放 NAS 本地。未擅自改 Dockerfile，
等王震定或下次构建时再处理。

- `web/static/style.css`：`.nav-version`（靠右、灰色小字）、
  `.nav-update`（橙色小 pill）。
- 总览页原有的 `#app-version` 小字与升级横幅（已是最新/有新版本/
  一键升级）**原样保留**。
