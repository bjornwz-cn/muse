- 缓存：`/data/upgrade/check.json`，TTL 6 小时；总览页打开时读缓存，过期时
  在 API 内同步重取（10 秒超时），不阻塞页面渲染（前端 JS 异步取）。

- 版本比较按数字段（0.1.10 > 0.1.9），允许 `v` 前缀与 `-beta` 后缀。

### 1.2 一键升级（只在他点按钮时执行，绝不自动触发）

- Web 端：`POST /api/upgrade/request` 校验目标版本 > 当前版本、无进行中的
  升级后，把请求写进数据卷 `/data/upgrade/request.json`（标志文件）。
  `GET /api/upgrade/status` 读状态文件供页面轮询（3 秒一次，显示阶段进度；
  成功 3 秒后刷新页面；失败显示原因与是否已回滚）。
- 触发机制：容器不能自己重启自己，也不挂 docker socket。NAS 侧 systemd timer
  每分钟跑 watcher（`scripts/upgrade-watcher.sh`），拾取标志文件后执行
  `scripts/upgrade.sh`。
- 升级脚本流程：取代码 → 构建新镜像 → 备份数据库 → 换 compose 重建 →
  验证 → 任一步失败则用上一版镜像重建回滚。
  - 取代码：优先用 VM 已同步的暂存目录（见 §5）；没有或版本不对时改试
    git 拉取（HTTP/1.1，两次重试）；都没有时失败并明说原因。
  - 构建：单次限时 15 分钟，失败重试一次（见 §6 的卡住教训）。
  - 备份：容器内 `VACUUM INTO /data/nas-curator.db.bak-<日期>-pre<新版>`
    （与 0.1.2/0.1.3 部署口径一致）。
  - 部署：用新版 fpk 里的 compose 覆盖安装路径（旧文件备份为
    `docker-compose.yaml.<旧版>-bak`），`docker compose -p nas-curator up -d
    --force-recreate`（沿用 0.1.2/0.1.3 的绕法，不用不可靠的 appcenter-cli stop）。
  - 验证：等 healthy（最长 5 分钟）+ 六页与 /api/dashboard 均 200 +
    /api/settings 含 effective_order 且 OCR 可达。
  - 回滚：恢复旧 compose、用上一版镜像重建、再验证；回滚成功则状态写
    failed + rolled_back=true；回滚也失败则写明需手动处理。回滚前置检查：
    上一版镜像不存在时拒绝升级（无回滚路）。
  - 升级前与升级后 request.json 都会被清理，不会重复触发；全程 flock
    防并发。

## 5. NAS 直连 GitHub 核实结论：git clone 不可靠，改走 VM 同步

| 通道 | 结果 |
|---|---|
| `git ls-remote https://github.com/bjornwz-cn/muse.git` | 通（HEAD 71a0b60） |
| `curl https://github.com` | 200（5.9 秒） |
| `curl https://api.github.com/...` | 通（404 仅因 VERSION 当时未推） |
| `curl https://raw.githubusercontent.com/...` | **不通**（15 秒与 30 秒两次超时） |
| `curl https://codeload.github.com/.../tar.gz` | 200 但 20 秒未下完（慢，未证伪） |
| `git clone --depth 1 --filter=blob:none --sparse`（HTTP/2） | **失败**：`HTTP/2 stream 1 was not closed cleanly` |
| `git clone`（HTTP/1.1） | **失败**：`curl 28 Failed to connect to github.com port 443 after 134052 ms` |

结论：NAS 出站到 GitHub 是**小请求通、大传输抖动**。muse 仓 `.git` 达 87MB，
clone 本来就重。**主路径改为 VM 侧同步**：

- `scripts/sync-code-to-nas.sh`（VM 上跑）：`git fetch origin` → HEAD 未变退出；
  变了则 `git archive origin/main nas-curator`（只取已提交的 nas-curator/ 子树，
  1.4MB，绝不含未提交改动与 `.env.local`——git archive 只含已跟踪文件）→
  经 SSH 隧道 tar 到 NAS `/vol2/@appshare/nas-curator/upgrade-work/stage` →
  核对 NAS 侧 VERSION 与远端一致。实测已同步两次（fe761d0、5c317eb）。
- VM 定时任务 `nas-curator-code-sync`：**每小时**跑一次（首次 2026-11-20 11:03）。
  成功（包括 HEAD 未变）时不向用户发消息；失败只记运行记录，下次重试。
- `upgrade.sh` 取代码顺序：暂存目录版本 == 目标 → 直接用；否则试 git 拉取
  （HTTP/1.1，两次重试）；都没有时失败并明说「VM 同步每小时一次，请稍后再试」。
- 同步脚本踩过一个坑：默认 ssh 在非交互环境下 `git fetch` 报
  `Host key verification failed`，须显式传与 git push 相同的 GIT_SSH_COMMAND
  （已修，见提交）。

## 6. torch 构建教训（两次 dry-run 失败后查清）

### 6.1 download.pytorch.org 下载卡住

dry-run 第 2 次：构建在下载 torch 2.15.0+cpu（209.5MB）处卡住，11 分钟无进展，
后被手动杀掉。第一次 0.1.4 构建时同一下载曾成功（约 3.5 分钟完成），属抖动。

### 6.2 阿里云 pytorch-wheels 不是合法的 pip 索引（已改回）

为绕开卡住，曾把 Dockerfile 的 `--index-url` 改为
`https://mirrors.aliyun.com/pytorch-wheels/cpu`。结果：

- 该 URL 不是 PEP 503 Simple 索引：`.../cpu/torch/` 返回的是镜像站 About 页，
  0 个包链接（TUNA、USTC 的同路径也未列出该包）。
- pip 在该源找不到任何包，**静默回落到 PyPI 的 CUDA 版 torch 2.15.0**
  （539MB）及数 GB nvidia 轮子（cudnn 519MB、cusparselt 170MB、nccl 等）。
  若放任构建完成，会得到一个与部署版不同的 CUDA torch 镜像。
- **已改回** `https://download.pytorch.org/whl/cpu`，并在 Dockerfile 注释里记下
  这次试错与原因。

### 6.3 根治：torch 钉死版本

`requirements-image.txt` 里 `torch` 原先未钉版本。现钉死 `torch==2.15.0+cpu`
（与已部署的 0.1.4 镜像内实际版本一致）：

- CPU 源可达时装到的就是 +cpu 版；
- CPU 源不可达时构建直接失败（找不到满足条件的版本），**不会静默装 CUDA 版**。
- 附带修掉的两个小问题：构建重试（单次限时 15 分钟，失败重试一次）与
  `status.json` 里非终态残留旧 `finished_at`（现已清空）。

### 6.4 构建缓存观察（未深究，只记录）

pip 层在两次构建间未命中缓存（每次都重新下载全部轮子），原因未确定；
影响只是每次升级构建多花几分钟，不影响正确性。

   导致命令 255 退出——`pkill -f` 带完整命令行模式时须避开自匹配）。
   正常流程不受影响（脚本不被外杀时 timeout 会兜底）；下次可加 trap 清理子进程。
